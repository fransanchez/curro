## 1. Summary

The first user-visible use of Gemma 3n. When `ReadAllUnreadWhatsAppHandler`
finds > 8 unread WhatsApps (already detected by US-032 / SF-4.8), instead
of speaking the existing `copy_many_unread` line ("Tienes muchos
mensajes. ¿Te los leo todos o solo los de alguien?"), Curro produces a
**per-sender one-sentence summary** in his colloquial Spanish voice:
*"Tienes muchos mensajes nuevos. Te los resumo por persona. De Pepito:
te espera a las siete y te pide que lleves pan y vino. De Lucía: te
llama mañana, papá. De Carmen: pregunta cómo te encuentras."*

This is the first SF that *speaks* something generated by Gemma 3n.
Three principles drive the design:

1. **Graceful fallback is the load-bearing rule** — ANY failure
   (Gemma 3n cold-load fails, weights missing, OOM, malformed output)
   surfaces as the *existing* `copy_many_unread` line. The 4 GB worst
   case is functionally identical to today's behaviour.
2. **`copy_cold_model` is spoken at most once per turn** — and only when
   the cold-load is *expected to succeed* (i.e. weights are present);
   if weights are missing, we go straight to the fallback without
   teasing.
3. **The handler speaks the cold-model line directly via `TtsClient`,
   not via the coordinator** — a deliberate departure from the
   "all-speech-via-coordinator" pattern. Rationale: the handler is
   mid-execution; the cold-model line is a *pre-result* utterance, not a
   `HandlerResult`. Forcing it through the coordinator would require a
   handler→coordinator back-channel that doesn't exist. The brief
   acknowledges this and pins it as the right call.

The catalog is **unchanged**. `read_all_unread_whatsapp` stays as the
single user-visible function. The full `summarize_whatsapp_thread`
catalog function lands in Fase 3, not Phase 9 (spec §5).

**Why this matters for *this* user**: after a long lunch with his phone
face-down, Fran's father has 12 unread messages from 3 people. Without
this SF, Curro reads every message verbatim — that's ~2 minutes of
spoken text, by which point the user has forgotten the first message.
With this SF, Curro speaks a 10-second summary per person and the user
gets the gist immediately. *This is the entire point of having Gemma 3n
on-device.*

## 5. FSM States Touched

**None directly.** Everything happens inside the coordinator's existing
`Executing` state.

**Pin**: the `copy_cold_model` utterance is spoken FROM the handler
(not the coordinator) during `Executing`. The coordinator does NOT
transition to `ErrorRecovery` for this case — the cold-model path is
not an *error*, it's a *latency announcement*. The handler stays in
`Executing` (coordinator's view) until `generate()` resolves.

The FSM `ErrorRecovery` state is reserved for situations where Curro
*cannot* proceed (STT failure, FunctionGemma failure, invalid output);
the cold-model path can still proceed (after ~3–6 s), so it stays in
`Executing`.

## 7. On-device-model Impact

**This SF is the first production caller of Gemma 3n.** Key constraints:

- **Prompt size**: bounded by the > 8 threshold and the natural ceiling
  of unread WhatsApps in a single session (~30 in the worst plausible
  case). At 30 messages × ~40 tokens per message + header ≈ 1500
  tokens — comfortably below the engine's `MAX_TOKENS = 2048` ceiling.
- **Latency budget**: target < 6 s for `generate()` warm (per US-061);
  + ~4 s cold load on first turn. Total cold-path latency: ~10 s end
  to end, with the `copy_cold_model` line absorbing the user's
  perceived wait.
- **Memory**: ~2 GB active while Gemma 3n is loaded. `CurroApp.onTrimMemory`
  unloads on memory pressure (US-061); this handler doesn't manage
  memory directly.
- **PII boundary**: the prompt sent to Gemma 3n DOES contain message
  bodies and sender names (it has to — that's what's being summarised).
  These NEVER leave the device. The telemetry event uses bucketed
  counts only — see §8.7.
- **Output validation**: the engine returns raw text. `SummaryOutputCleaner`
  strips known LLM artefacts (bullet markers, surrounding quotes,
  echoed headers). If the cleaned output is empty or obviously broken
  (TBD: what does "broken" mean?), the brief defers to a future SF —
  Phase 9's contract is "if generate() returns success, we speak it".
  An adversarial output (e.g. the model echoes a system prompt) gets
  spoken; for a single-user prototype this is acceptable. The Fase-3
  `summarize_whatsapp_thread` catalog function will add stricter
  validation.

### 8.3 `WhatsAppSummaryPromptBuilder.kt`

```kotlin
package com.curro.app.handler.whatsapp

import com.curro.app.domain.model.WhatsAppMessage
import javax.inject.Inject
import javax.inject.Singleton

/**
 * Builds the Gemma 3n prompt for the WhatsApp summarisation path (US-062 / SF-9.3).
 *
 * Groups messages by sender, sorted most-recent-active-first (same ordering as
 * `ReadAllUnreadWhatsAppHandler`'s existing flow so the summary mirrors the
 * verbatim-read flow). Wraps in a Spanish system prompt instructing Curro's
 * voice (colloquial, Andalusian, factual — no invention).
 *
 * **PII**: the prompt DOES contain message bodies and sender names. This is
 * unavoidable — that's the input to the summary. The prompt NEVER leaves the
 * device. Verified by the engine's PII boundary docstring.
 *
 * Testing: golden-string match in `WhatsAppSummaryPromptBuilderTest`.
 */
@Singleton
class WhatsAppSummaryPromptBuilder @Inject constructor() {
    fun build(messages: List<WhatsAppMessage>): String {
        if (messages.isEmpty()) return EMPTY_FALLBACK_PROMPT
        val groups = messages
            .groupBy { it.sender }
            .map { (sender, msgs) -> sender to msgs.sortedBy { it.timestamp } }
            .sortedByDescending { (_, msgs) -> msgs.maxOf { it.timestamp } }

        val context = groups.joinToString(separator = "\n\n") { (sender, msgs) ->
            buildString {
                append("De ").append(sender).append(":\n")
                msgs.forEach { msg ->
                    append("- ").append(msg.text).append('\n')
                }
            }.trimEnd()
        }
        return PROMPT_TEMPLATE.format(context)
    }

    private companion object {
        // Pinned template — golden-string-tested.
        val PROMPT_TEMPLATE = """
            Eres Curro, un asistente para una persona mayor andaluza. Hablas en castellano
            coloquial, cálido y cercano, sin inventar nada.

            Te paso una lista de mensajes nuevos de WhatsApp, agrupados por remitente.
            Resume cada remitente en una sola frase corta. Empieza cada frase con
            "De <nombre>:" y termínala con punto. Separa los remitentes por un espacio.
            No añadas saludos, despedidas, ni comentarios tuyos. Solo el resumen.

            Mensajes:
            %s

            Resumen:
        """.trimIndent()

        // Defensive — the handler never calls this with an empty list, but the
        // builder doesn't crash either.
        const val EMPTY_FALLBACK_PROMPT = "Resume: (sin mensajes). Salida:"
    }
}
```

### 8.4 `SummaryOutputCleaner.kt`

```kotlin
package com.curro.app.handler.whatsapp

import javax.inject.Inject
import javax.inject.Singleton

/**
 * Strips known LLM artefacts from Gemma 3n's raw summary output (US-062 / SF-9.3).
 *
 * Applied to every successful `TextGenEngine.generate` result before TTS.
 * Conservative — only removes things the model is *known* to add (quotes,
 * bullet markers, echoed headers, excess whitespace). Does NOT validate
 * semantic correctness; for the prototype that's acceptable (a single-user
 * validation instrument).
 *
 * Testing: 6 golden-string cases in `SummaryOutputCleanerTest`.
 */
@Singleton
class SummaryOutputCleaner @Inject constructor() {
    fun clean(raw: String): String {
        var out = raw.trim()

        // Strip echoed headers.
        ECHOED_HEADERS.forEach { header ->
            if (out.startsWith(header, ignoreCase = true)) {
                out = out.removePrefix(header).trimStart(':', ' ', '\n')
            }
        }

        // Split by newline, strip leading bullets per line, then re-join with ". ".
        val lines = out.lines()
            .map { line -> line.trim().removePrefix("- ").removePrefix("* ").trim() }
            .filter { it.isNotBlank() }
        out = lines.joinToString(". ")

        // Strip surrounding quotes (straight + curly).
        SURROUNDING_QUOTES.forEach { (open, close) ->
            if (out.startsWith(open) && out.endsWith(close)) {
                out = out.removePrefix(open.toString()).removeSuffix(close.toString())
            }
        }

        // Collapse runs of whitespace (newlines, tabs, multiple spaces) to one space.
        out = WHITESPACE_RUN.replace(out, " ").trim()

        return out
    }

    private companion object {
        val ECHOED_HEADERS = listOf("Resumen por persona", "Resumen", "Salida")
        val SURROUNDING_QUOTES = listOf('"' to '"', '“' to '”', '\'' to '\'')
        val WHITESPACE_RUN = Regex("\\s+")
    }
}
```

### 8.5 `ReadAllUnreadWhatsAppHandler.kt` — modified

```kotlin
class ReadAllUnreadWhatsAppHandler
    @Inject
    constructor(
        private val notifications: NotificationRepository,
        private val accessGate: NotificationAccessGate,
        @ApplicationContext private val context: Context,
        // NEW dependencies (US-062 / SF-9.3):
        private val textGenEngine: TextGenEngine,
        private val modelFiles: ModelFiles,  // or via injected ModelFilesProvider; see US-061 pin
        private val promptBuilder: WhatsAppSummaryPromptBuilder,
        private val cleaner: SummaryOutputCleaner,
        private val ttsClient: TtsClient,    // for the cold-model utterance
        private val telemetry: TelemetrySink,
    ) : FunctionHandler {
        override val functionName: String = "read_all_unread_whatsapp"

        @Suppress("ReturnCount", "CyclomaticComplexMethod")
        override suspend fun handle(call: FunctionCall): HandlerResult {
            if (!accessGate.isGranted()) {
                return HandlerResult.Failed(
                    context.getString(R.string.copy_perm_missing_notifs),
                    CurroError.NotificationAccessMissing,
                )
            }
            val all = notifications.allUnread.first()
            val misses = notifications.parseMissCount.first()

            if (all.isEmpty() && misses > 0) {
                return HandlerResult.Spoken(context.getString(R.string.copy_whatsapp_parse_miss))
            }
            if (all.isEmpty()) {
                return HandlerResult.Spoken(context.getString(R.string.copy_no_unread))
            }
            if (all.size > MANY_THRESHOLD) {
                return summariseOrFallback(all)   // US-062 / SF-9.3
            }

            // ≤ 8 path unchanged — same buildHeader / buildGroupSpeech logic as before.
            // ... (existing code) ...
        }

        // ── US-062 / SF-9.3 — summarisation branch ────────────────────────────

        private suspend fun summariseOrFallback(unread: List<WhatsAppMessage>): HandlerResult {
            val weightsPresent = modelFiles.isGemma3nAvailable()
            val isReady = textGenEngine.isReady.value
            var coldSpoken = false

            // Speak the cold-model line only when the load is expected to succeed.
            if (!isReady && weightsPresent) {
                ttsClient.speak(context.getString(R.string.copy_cold_model))
                coldSpoken = true
            }

            val prompt = promptBuilder.build(unread)
            val result = textGenEngine.generate(prompt)

            return result.fold(
                onSuccess = { rawOutput ->
                    val cleaned = cleaner.clean(rawOutput)
                    emitSummaryTelemetry(
                        outcome = "success",
                        senderCount = unread.groupBy { it.sender }.size,
                        messageCount = unread.size,
                        coldSpoken = coldSpoken,
                    )
                    HandlerResult.Spoken(
                        context.getString(R.string.copy_summary_intro) + " " + cleaned,
                    )
                },
                onFailure = { err ->
                    val outcome = when (err) {
                        is CurroError.ModelCold -> "fallback_cold"
                        is CurroError.OutOfMemory -> "fallback_oom"
                        else -> "fallback_invalid_output"
                    }
                    emitSummaryTelemetry(
                        outcome = outcome,
                        senderCount = unread.groupBy { it.sender }.size,
                        messageCount = unread.size,
                        coldSpoken = coldSpoken,
                    )
                    HandlerResult.Spoken(context.getString(R.string.copy_many_unread))
                },
            )
        }

        private fun emitSummaryTelemetry(
            outcome: String,
            senderCount: Int,
            messageCount: Int,
            coldSpoken: Boolean,
        ) {
            telemetry.event(
                "summary_generated",
                mapOf(
                    "outcome" to outcome,
                    "sender_count_bucket" to bucketSenderCount(senderCount),
                    "message_count_bucket" to bucketMessageCount(messageCount),
                    "cold_spoken" to coldSpoken,
                ),
            )
        }

        private fun bucketSenderCount(n: Int): String = when {
            n <= 1 -> "1"
            n == 2 -> "2"
            n == 3 -> "3"
            else -> "4plus"
        }

        private fun bucketMessageCount(n: Int): String = when {
            n <= 12 -> "9to12"
            n <= 20 -> "13to20"
            else -> "21plus"
        }

        // ── existing helpers unchanged ─────────────────────────────────────────
        // buildHeader / buildGroupSpeech / bodySpeech …

        private companion object {
            const val MANY_THRESHOLD = 8
        }
    }
```

> **Pin: why the handler calls `ttsClient.speak()` directly for
> `copy_cold_model`.**
>
> Every other speech in Curro goes via the coordinator (the coordinator
> calls `ttsClient.speak()` with the `HandlerResult.Spoken.speech`).
> This SF deliberately departs from that pattern for the cold-model
> line. The reasons:
>
> 1. The cold-model line is *pre-result*, not a result. There is no
>    `HandlerResult` to wrap it in — the handler hasn't finished yet.
> 2. Returning a "I'm about to wait" `HandlerResult` would require a
>    coordinator-handler back-channel (e.g. a `flow<String>` from the
>    handler) that does not exist and would touch the FSM grammar.
> 3. The coordinator is already in `Executing` waiting for the handler
>    to return — it's not in a state where it can naturally interleave
>    a TTS call.
> 4. The handler injects `TtsClient` cleanly (Hilt-bound, already used
>    by the coordinator) so there's no new wiring.
> 5. The handler is the natural owner of the latency knowledge (it
>    knows the model is cold; the coordinator does not).
>
> The cost: the coordinator doesn't *know* the handler spoke. This is
> acceptable for `copy_cold_model` because:
> - The coordinator doesn't need to know (it's still in `Executing`).
> - Telemetry captures `cold_spoken` directly via `summary_generated`.
> - No double-speaking risk because the coordinator's speech happens
>   later (on the eventual `HandlerResult.Spoken`).
>
> If a future SF needs more handler-mid-execution speech (e.g. a
> per-step status line), the right move is to introduce a proper
> `HandlerResult.Progress(speech: String)` channel — but that's
> over-engineering for a single one-shot utterance.

## 11. Design Notes

- **Why `summary_intro` as a separate string** (not concatenated into
  the cleaner output): the intro is Curro's voice and is constant; the
  generated content varies. Keeping them separate lets the
  brand-design team tune the intro without re-prompting Gemma 3n; lets
  the cleaner stay focused on artefact stripping; lets the test
  golden-string match the intro deterministically while the generated
  content stays flexible.
- **Why bucketed counts in telemetry**: spec §12 PII boundary. The
  exact count of unread messages is mildly identifying (you can profile
  usage patterns). Buckets give us "the distribution is mostly 9to12"
  insight without enabling per-user correlation.
- **Why the cleaner is conservative**: aggressive cleaning would risk
  dropping useful sentence fragments. The prototype's bar is "spoken
  Spanish that the user understands"; the Fase-3 `summarize_whatsapp_thread`
  function will add stricter validation if needed.

## 12. Performance Considerations

- **Cold path**: ~4 s load + ~3 s generate ≈ 7 s end-to-end *after*
  the cold-model utterance. The user perceives ~3 s wait (the
  utterance covers the rest).
- **Warm path**: ~3 s generate ≈ 3 s end-to-end. Comparable to or
  faster than the verbatim-read path for > 8 messages.
- **Memory**: handled at the engine layer (US-061). The handler is
  memory-neutral.
- **Concurrency**: the engine serialises via its mutex. The handler
  does NOT add a mutex.
- **TTS**: the `ttsClient.speak(copy_cold_model)` call is fire-and-go
  (TTS is async); the handler does NOT await its completion before
  calling `generate()`. The two operations run in parallel —
  intentionally — so the perceived latency is minimised. If TTS races
  ahead and finishes before `generate()`, that's fine (silence is
  acceptable for the remaining wait — the user already heard the
  utterance).

**Sequencing pin**: this SF is the third commit in the Phase-9 batch.

`TextGenEngine` is injectable.

**Pre-emptive answer to "why not check `isGemma3nAvailable()` BEFORE
speaking the cold-model line in Flow 3?"**: the brief explicitly says
to check it — see Flow 3 + the AC `unreadGt8_textGenWeightsMissing_fallsBackToCopyManyUnread_noColdLine`.
The handler's order is: (a) check `weightsPresent`; (b) if cold AND
weights present → speak the line; (c) call `generate()` regardless
(the engine itself does the same check + returns `ModelCold` cleanly).

**Pre-emptive answer to "what if `generate()` takes > 30 s?"**: out of
scope here. Phase 9 doesn't add a timeout — the engine's mutex holds
the call indefinitely. If the user gets impatient, the FSM rule
"interrupt by mic press" cancels the coordinator's `Executing` state
(SF-5.3). Hardening this with a timeout is a future SF if validation
surfaces it.
