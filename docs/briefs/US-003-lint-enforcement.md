## Summary

Take the lint plugins that US-001 *wired* (`org.jlleitschuh.gradle.ktlint` 12.1.x
and `io.gitlab.arturbosch.detekt` 1.23.x, both applied in `app/build.gradle.kts`;
a `detekt { config.setFrom(file("detekt.yml")) }` block; an `app/detekt.yml`
generated by `./gradlew detektGenerateConfig`; an `.editorconfig` at the repo
root with `indent_size = 4`, `max_line_length = 120`, the
`ktlint_function_naming_ignore_when_annotated_with = Composable` Compose
exception, and `ktlint_standard_no-wildcard-imports = enabled`) and turn them
into the project's actual **quality bar** — config relocated to its canonical
project location, the 4 detekt 1.23.x config-validator deprecation warnings
that have been carried since US-001 resolved, Compose-friendly tuning applied
over the defaults, a baseline file in place to absorb future legitimate
exceptions, build-failure policy explicit (ktlint fails on any violation;
detekt fails on any finding outside the baseline), enforcement proved by a
deliberately-introduced violation, and the "No Double Padding" custom rule
**explicitly deferred** in writing.

This story has **no user-visible value** for Fran's father. The value is
operational: every SF from SF-0.4 onwards lands on a project where Kotlin
style and code-quality regressions break CI on the same day they're
introduced, rather than silently accumulating against the senior-UX contract
the linters will eventually police (no `!!`, no raw `Color(0xFF…)` / `.sp`
/ `.dp` literals, no hard-coded Spanish strings, etc. — the lint *system*
goes in here; the Curro-specific *custom rules* go in later, deliberately).

Spec ref: `docs/curro-spec-v1.0.md` §14 (stack & build order — the spec
doesn't prescribe lint specifics; this SF locks in the toolchain the project
chose). Master-plan ref: SF-0.3.

## Scope

### In Scope

- **Move the detekt config to its canonical location.** US-001 placed the
  generated config at `app/detekt.yml` and pointed `detekt { config.setFrom(...) }`
  at it. US-003 moves it to `config/detekt/detekt.yml` (the de-facto convention
  for detekt configs across Android projects — easier for editor plugins to
  discover, keeps `app/` free of build-tool config), updates the
  `app/build.gradle.kts` reference, and **deletes** the old file. The old
  location must not survive as a stale copy.
- **Resolve the 4 detekt-1.23.x config-validator deprecation warnings.** These
  warnings have been observed on every `./gradlew detekt` run since US-001
  landed and were carried forward into US-002 unchanged. They are detekt's
  own `ConfigValidator` complaining about deprecated config keys (e.g. a rule
  property that detekt renamed between minor versions, or a section name that
  shifted); they are **not** Curro source-code problems. The developer:
  1. Runs `./gradlew detekt --info` (or `--debug`) from the post-US-002 state
     to capture the exact 4 warning messages and the lines they point at in
     `config/detekt/detekt.yml`.
  2. For each one, looks up the corresponding detekt 1.23.x rule docs (or the
     PR that deprecated it) and applies the renamed/replacement key — keeping
     the *meaning* identical (this SF does not silently change rule behaviour
     to dodge a warning).
  3. Adds an inline comment `# was: <old-key> (renamed in detekt 1.23.x)`
     next to each replaced key so the next reader knows why the change was
     made.
  4. Re-runs `./gradlew detekt` and confirms the output is **zero deprecation
     warnings**.
- **Apply Curro-shaped tuning over the default export.** The exported default
  config is the floor; Curro tunes the following deliberately (each one with
  a one-line comment in `config/detekt/detekt.yml` explaining why):
  - `style.MaxLineLength.maxLineLength: 120` — already set in the default
    export at 120; **kept** and aligned with `.editorconfig`'s `max_line_length`.
    Comment: `# aligned with .editorconfig`.
  - `style.WildcardImport.active: true` — kept; `excludes` keeps the
    test/androidTest exclusion already in the default. Comment: `# ktlint
    also forbids wildcards via .editorconfig — detekt is the belt to ktlint's
    braces`.
  - `naming.FunctionNaming.ignoreAnnotated: ['Composable']` — kept; already in
    the default export. Comment: `# composables use PascalCase by Compose
    convention — same exception as .editorconfig`.
  - `potential-bugs.UnsafeCallOnNullableType.active: true` — kept active
    (already on by default); this is the rule that catches `!!`, which
    `CLAUDE.md` → "Coding Standards" forbids in new code. Comment: `# CLAUDE.md
    forbids !! — this rule is the enforcement`.
  - `style.MagicNumber.active: true` — kept; default `ignoreNumbers` list
    (`-1`, `0`, `1`, `2`) is sufficient for now; the developer must **not**
    pre-emptively widen it to dodge expected future warnings on `.dp`/`.sp`
    literals — those are the kind of warning we *want* to see when feature
    code lands so we can address each consciously.
  - `complexity.LongMethod.threshold: 60` — kept at the default 60 even though
    `CLAUDE.md` says "short functions (< 20 lines)". Rationale: 20 is an
    *aspirational* style note; 60 is the *hard* lint gate. Comment: `# CLAUDE.md
    aims for < 20 lines as a style target; 60 is the hard fail bar so the
    detector catches genuinely-too-long methods without spamming on every
    composable`.
  - `complexity.LargeClass.threshold: 600` — kept default.
  - `complexity.LongParameterList.{functionThreshold: 6, constructorThreshold:
    7, ignoreDataClasses: true}` — kept default; `ignoreDataClasses: true` is
    important because Curro's domain models (`FunctionCall`,
    `HandlerResult.Spoken`, `WhatsAppMessage`, …) will have wide constructors
    by design.
  - `complexity.TooManyFunctions.threshold*: 11` — kept default. (Handlers and
    use cases stay small; the threshold is the floor against god-objects.)
  - `formatting:` section — **not added**. Detekt has an optional
    `detekt-formatting` rule set that wraps ktlint rules; adding it would
    duplicate ktlint and double-report. ktlint already owns Kotlin formatting
    in this project; detekt stays out of that lane. Comment in the YAML
    explaining the deliberate absence.
  - `libraries:` / `ruleauthors:` sections — also **not added**. They target
    library authors and are noise for an app.
  - Every other section — `comments`, `coroutines`, `empty-blocks`,
    `exceptions`, `naming`, `performance`, `potential-bugs`, `style` —
    stays at the default `./gradlew detektGenerateConfig` shape. **The
    developer must not "improve" sections that are not on the list above**;
    rule tuning is an explicit, traceable activity — every active tune
    documented in the YAML and listed in this brief.
- **Generate a baseline file at `config/detekt/baseline.xml`** by running
  `./gradlew detektBaseline` after the tuning pass is complete. The expected
  result on the post-US-002 scaffold is an **empty or near-empty** baseline
  (the codebase is the Hilt smoke test + a `MainActivity` showing `Text("Curro")`
  + a `CurroApp` class + the `CoroutineModule` + `Qualifiers.kt` — nothing
  else). If the baseline ends up with more than ~5 entries, the developer
  pauses and asks: is there a rule that's mis-tuned? The baseline is for
  *legitimate* future exceptions (e.g. an annotated `Suppress` won't always
  cover what we need), not for sweeping current findings under the rug.
- **Wire `app/build.gradle.kts`'s `detekt { }` block** to:
  - `config.setFrom(rootProject.file("config/detekt/detekt.yml"))` — points to
    the new location (replaces US-001's `file("detekt.yml")`).
  - `baseline.set(rootProject.file("config/detekt/baseline.xml"))` — points to
    the baseline file generated above.
  - `buildUponDefaultConfig = false` — kept from US-001 (we ship a fully
    self-contained config; relying on the default *and* overriding it leads to
    surprises on detekt minor upgrades).
  - Reports: `html`, `xml`, `sarif` — all enabled (HTML for humans, XML for IDE
    plugins, SARIF for GitHub code-scanning if we ever want it later; cost is
    cents). Output: `app/build/reports/detekt/`.
- **Address the detekt-K2 experimental flag.** Detekt 1.23.x supports K2 (the
  Kotlin 2.x compiler frontend) as an experimental opt-in via the `detekt {
  enableCompilerPlugin = true }` flag (or the equivalent `-Pdetekt.enable-K2=true`
  Gradle property — exact name varies by detekt patch version; the developer
  consults the detekt 1.23.x release notes for the canonical flag name as
  of 2026-05-13). The developer makes **one** of the following two decisions,
  explicitly, in writing in `app/build.gradle.kts`:
  - **Option A — turn it on** with a one-line code comment justifying it as
    stable on detekt 1.23.x as of 2026-05-13 (cross-reference: the detekt
    release notes / GitHub issue stating the flag is no longer experimental).
  - **Option B — leave it off** with a one-line code comment saying so and
    deferring to a later SF or a chore commit once it's no longer marked
    experimental.
  Silent reliance on whichever happens to be the default is forbidden — the
  acceptance criterion is an explicit, traceable choice.
- **Enforcement policy — make the build fail.** This is the actual *enforcement*
  payoff of US-003 (US-001's bar was only "the plugins run to completion"). The
  policy:
  - `./gradlew ktlintCheck` — **fails the build on any violation**. This is the
    `org.jlleitschuh.gradle.ktlint` plugin's *default* behaviour; the developer
    must verify no `ignoreFailures = true` was added inadvertently. The
    counterpart `./gradlew ktlintFormat` (auto-fix) stays available for the
    developer; CI runs `ktlintCheck`, which does not auto-fix and does fail
    on violations.
  - `./gradlew detekt` — **fails the build on any finding not in the
    baseline**, via `build { maxIssues: 0 }` in `config/detekt/detekt.yml`
    (already at 0 in the default export — verify it stays at 0; no relaxation
    permitted by this SF). Findings at `Severity.Warning` will not fail by
    default — this is the part most teams get confused by, and the brief calls
    it out: tuned rules at `Severity.Error` do fail; rules left at
    `Severity.Warning` produce report output but do not break the build.
    **For Curro, the default severities in the exported config are the right
    floor for the prototype — don't escalate every Warning to Error in this SF;
    pick that fight on a per-rule basis as it bites.**
  - `config.warningsAsErrors: false` — kept at the default (which is what we
    just said). The brief documents this explicitly so the developer doesn't
    flip it "because warnings as errors sounds correct".
- **Prove enforcement works with a deliberately-introduced violation.** This is
  one of the acceptance criteria, performed by the developer once at the end
  of the SF and **not committed**:
  - Temporarily add `val unsafe: String? = null; val x = unsafe!!` to
    `app/src/main/java/com/curro/app/util/Tmp.kt` (a throwaway file that gets
    deleted immediately after).
  - Run `./gradlew detekt` and confirm it exits non-zero with a
    `UnsafeCallOnNullableType` finding pointing at that line.
  - Temporarily rename a private property to a `PascalCase` name (which is
    invalid for non-const properties — `private val FooBar = "x"`); run
    `./gradlew ktlintCheck` and confirm it exits non-zero with a
    `property-naming` violation.
  - Delete the throwaway file; re-run `./gradlew ktlintCheck detekt` and
    confirm green.
  - Record the two failing console outputs in the PR description as evidence
    the policy is actually enforced (not just claimed).
- **`.editorconfig`**: kept exactly as US-001 left it unless the developer
  needs a new key for a specific rule. **Any new key must have a one-line
  comment explaining why** (e.g. `ktlint_standard_function-signature = disabled
  # function-signature rule is too aggressive on Compose previews`). The
  developer must **not** sprinkle ad-hoc disables to make warnings go away —
  if a rule is wrong for Curro, disable it in `config/detekt/detekt.yml` (for
  detekt) or `.editorconfig` (for ktlint) and document why; if a rule is right
  for Curro but inconvenient in the test sources, exclude only the test paths
  (the default export already does this for most rules — verify, don't bulk
  copy).
- **Format the existing source code with `./gradlew ktlintFormat`** once at
  the end of the SF and commit the formatting fixes. On a fresh clone of the
  resulting commit, `./gradlew ktlintCheck` must pass *without* needing a
  preliminary `ktlintFormat` — the developer is responsible for committing
  the formatted source.
- **Measure the build-time impact.** Once at the end of the SF: run
  `./gradlew clean ktlintCheck detekt` on a warm Gradle cache against the
  post-US-003 state, record the wall-clock time, and compare it to the same
  command on the pre-US-003 state (US-002 HEAD). The delta should be < 10 s
  on a typical dev machine. The brief calls for this as an *informational*
  acceptance criterion, not a hard gate — if it's higher, the developer
  notes it in the PR for visibility but does not block on it.

### Out of Scope (each is its own later SF)

- **The "No Double Padding" custom detekt rule.** `CLAUDE.md` and the
  `compose-patterns` skill say children must not add their own `Scaffold` /
  `TopAppBar` / `statusBarsPadding()` (the parent `CurroNavHost` applies the
  insets once via its `innerPadding`; a child that re-adds them double-pads
  the top). A custom detekt rule that flags this is technically possible
  but **non-trivial** — it requires:
  1. A separate Gradle module (e.g. `:detekt-rules-curro` or `tools/detekt-rules/`).
  2. A `Rule` subclass extending `io.gitlab.arturbosch.detekt.api.Rule` that
     walks the PSI looking for `Scaffold` / `TopAppBar` / `statusBarsPadding`
     calls inside `@Composable` functions whose top-level layout already
     resides under a `NavHost`-rooted scaffold (the rule needs a heuristic
     for "is this a child screen?" — not free).
  3. A `RuleSetProvider` to register the rule.
  4. A `detekt-rules.jar` artifact wired into `app/build.gradle.kts`'s
     `detektPlugins(libs.curro.detekt.rules)` configuration.
  5. Unit tests for the rule itself, against fixture composables.
  This is roughly a half-day of work and **should land after the FSM + the
  real screens exist** so the rule has real targets to test against. Target:
  the same SF that introduces `CurroNavHost` and the first non-trivial child
  screen (currently SF-0.6 + SF-1.1+ for routes; the rule arrives once a
  scope of "child screens" actually exists — probably a new SF in the
  range `SF-5.x` *or* its own `SF-tooling.1` once Phase 0/1 are done).
  **The brief documents the punt in the *Implementation Notes* section
  below**; the developer must not silently take it on.
- **Other Curro-specific custom rules.** Same logic — defer:
  - "No raw `Color(0xFF…)` literals in composables" (rule lives outside of
    `CurroTheme`/`CurroColorScheme` files) — punted; lands after SF-0.4
    introduces the theme tokens so there's something to compare against.
  - "No hard-coded Spanish strings in composables" — punted; lands after
    SF-0.7's `COPY.*` table exists so the rule has something to whitelist
    *through*.
  - Each of these can be its own micro-SF (`SF-tooling.x`) or rolled into
    a "lint hardening pass" later. Out of scope for US-003.
- **CI workflow changes.** `.github/workflows/ci.yml`'s existing
  `./gradlew ktlintCheck detekt` step is sufficient. No SARIF upload, no
  JUnit XML upload of detekt results — those are nice-to-haves for later,
  not required for the enforcement policy to bite. The brief says "no CI
  YAML edit needed in this SF" out loud.
- **Pre-commit hooks (`pre-commit-hook` Gradle task, `.husky/` scripts,
  etc.).** Pre-commit hooks were mentioned in the master-plan SF-0.3
  description ("a pre-commit-friendly `./gradlew ktlintCheck detekt`
  task"). The current `./gradlew ktlintCheck detekt` already serves that
  purpose — there is no separate "pre-commit task" needed; the developer
  is free to wire `.git/hooks/pre-commit` locally to run it. **Adding a
  shared pre-commit hook framework (`pre-commit` Python tool, `lefthook`,
  `husky` for Kotlin via `gradle-git-hooks-plugin`, etc.) is out of
  scope** — opinionated, has install/onboarding cost, and the team is
  Fran + Claude. Defer; revisit if a contributor onboarding doc asks for
  it.
- **Jacoco / code-coverage gates.** Out of scope; coverage is a Phase-1+
  question once there's feature code to cover (US-001's brief already
  said as much).
- **R8 / minification tuning.** Out of scope; lives with telemetry +
  models (SF-0.8 + SF-3.x).
- **lint (Android Lint via `lintOptions { }`).** Android Lint is AGP's
  native lint, separate from ktlint + detekt. It's already wired by AGP
  defaults; US-003 does not tune it. (A `lint { abortOnError = true }`
  pass is a sensible later SF — `SF-tooling.x` — but not here.)

## User Flows

US-003 has **no end-user flow**. The "users" are a Curro developer running
Gradle locally and the CI runner on GitHub Actions. The two flows are:

### Flow 1: Developer runs lint locally and a real violation is caught

1. Developer makes an edit that includes a `!!` operator in some hot path.
2. Developer runs `./gradlew detekt` (or just `./gradlew check` — both
   trigger the detekt task as part of AGP's check chain).
3. detekt exits non-zero with a `UnsafeCallOnNullableType` finding pointing
   at the line.
4. Developer sees the rendered error (path + line + rule), fixes it (the
   right move for Curro is `?.let { … }` or `requireNotNull(x) { "msg" }`
   — `CLAUDE.md` codifies this), re-runs detekt, green.
5. Developer then commits.

### Flow 2: Developer runs lint locally on perfectly-formatted code

1. Developer runs `./gradlew ktlintCheck detekt`.
2. Both tasks run; detekt produces the report under
   `app/build/reports/detekt/detekt.{html,xml,sarif}` (which the developer
   doesn't usually open — the console output is fine for the empty
   scaffold).
3. Both exit 0; developer moves on.

### Flow 3: CI catches a regression

1. A future SF's PR introduces a `Color(0xFF…)` literal in a composable
   (we don't have a custom rule for this yet — but the developer of that
   SF *also* introduces a `!!`).
2. CI runs `.github/workflows/ci.yml`'s lint step → `./gradlew ktlintCheck
   detekt`.
3. detekt exits non-zero on the `!!`; CI fails.
4. PR shows red; reviewer flags it before merge.
5. PR author fixes the `!!`, re-pushes; CI green.

## Performance Considerations

- Detekt is type-resolution-aware by default in 1.23.x (it walks the
  Kotlin compiler frontend); on a near-empty scaffold this is cheap
  (~2–4 s warm). On a populated codebase it grows, but stays under the

- ktlint is fast (Kotlin formatting only, no type resolution) — < 1 s on

- The baseline file is read once per run; cost is negligible.
- No runtime impact — these tasks do not run at app runtime.

### Order of operations (developer-facing checklist)

1. Branch off `main` per US-003 if a new branch is requested (the PM did
   not request one for this SF — the work is small enough to land
   directly on the working branch; the developer asks before creating
   one anyway).
2. From the post-US-002 state, run `./gradlew detekt --info` and capture
   the 4 deprecation-warning lines into a scratch note.
3. Move `app/detekt.yml` → `config/detekt/detekt.yml` (`git mv`); update
   `app/build.gradle.kts`'s `detekt { config.setFrom(...) }`; delete
   the old reference; run `./gradlew detekt` to confirm it still
   discovers the config in its new location.
4. Resolve the 4 deprecation warnings one at a time, adding a `# was:
   <old-key>` comment next to each replaced key. Re-run
   `./gradlew detekt` after each to confirm the warning count drops; at
   the end, the output should be zero deprecation warnings.
5. Apply the Curro tuning listed in *Scope → In Scope* — every change
   gets a one-line YAML comment. Re-run; confirm green.
6. Make the explicit K2 decision: add the `enableCompilerPlugin` setting
   (on or off) in `app/build.gradle.kts`'s `detekt { }` block with the
   justifying one-line code comment.
7. Generate the baseline: `./gradlew detektBaseline`. Inspect the
   resulting `config/detekt/baseline.xml` — expect empty / near-empty.
   If it's not, pause: a rule is over-firing on the scaffold; tune
   the rule (back in step 5) rather than absorbing the findings into
   the baseline. Set `baseline.set(rootProject.file("config/detekt/baseline.xml"))`
   in `app/build.gradle.kts`'s `detekt { }` block.
8. Wire HTML/XML/SARIF reports in the `detekt { }` block (or via
   `tasks.withType<Detekt>().configureEach { reports { ... } }` — the
   developer picks whichever shape detekt 1.23.x's Gradle plugin
   accepts).
9. Run `./gradlew ktlintFormat` once; commit any formatting fixes
   separately so the diff is easy to read.
10. Run `./gradlew ktlintCheck detekt` — expect green on a fresh clone.
11. **The deliberate-violation acceptance step**: add the two violations
    described above, capture the failing console output (these are the
    PR-description evidence), then delete the violations and confirm
    green.
12. Measure `./gradlew clean ktlintCheck detekt` wall-clock time on the
    post-US-003 state vs. pre; record the delta in the PR description.
13. Commit; tick the AC checklist; open the PR.

### The "No Double Padding" custom-rule punt — what to do *not* in this SF

The custom rule is non-trivial. To save the developer of the eventual SF
half a day of false starts, here's the shape it will take when it lands:

- A new Gradle module at `tools/detekt-rules/` (or a similarly-named
  location — keep it under a `tools/` umbrella so it doesn't clutter
  `app/`). Plugin: `kotlin("jvm")`, dependencies: `io.gitlab.arturbosch.detekt:detekt-api`
  (the public API for writing custom rules) at the same 1.23.x version
  as the app.
- A `Rule` subclass — e.g. `NoDoublePadding` — that overrides
  `visitNamedFunction(function)` and walks the function body. It needs
  a heuristic for "this composable is a child screen" (e.g. "function is
  `@Composable`, function name ends in `Screen` or is reachable from a
  `NavHost` `composable("...") { ... }` block"; the latter is harder
  without inter-file analysis — the rule may start with the simpler
  name-pattern heuristic). It flags any call to `Scaffold`,
  `TopAppBar`, `statusBarsPadding`, `navigationBarsPadding`,
  `safeContentPadding`, etc. inside such a function.
- A `RuleSetProvider` registering the rule under id
  `curro-compose-conventions`.
- Wire it from `app/build.gradle.kts` via
  `detektPlugins(project(":tools:detekt-rules"))`.
- Unit tests at `tools/detekt-rules/src/test/` using `detekt-test`
  utilities — golden fixtures of (a) a child screen that violates,
  (b) a `CurroNavHost`-level scaffold that's *allowed* to add insets,
  (c) a screen with `statusBarsPadding` legitimately because it's not
  a `NavHost` child (none today, but the rule needs to allow it).
- Add a section to `config/detekt/detekt.yml` enabling the rule under
  its `curro-compose-conventions` block.

Target SF: **after** SF-0.6 (`CurroNavHost`) and **after** SF-1.x's
first real screens land — probably `SF-tooling.1` or rolled into a
"lint hardening" pass between Phase 1 and Phase 2.

Same shape applies to the future "no raw `Color(0xFF…)` literal" rule
and "no hard-coded Spanish strings" rule — each will reuse the
`tools/detekt-rules/` module once it exists.

### Why the architect review was skipped

US-003 is configuration tuning. No domain/data/handler/assistant code
lands. No new architecture decisions surface: the package layout is
unchanged, the DI graph is unchanged, the manifest is unchanged, no
new model integration, no new system permission. The only design-ish
call is whether to take on the custom-rule punt — resolved in this
brief as a hard "no, later, here's the shape it'll take when it
does land". If the developer hits a genuine architectural snag mid-SF
(e.g. detekt-K2 is unstable enough to need a phased migration plan;
or the rename of a deprecated key changes rule behaviour in a way
that requires a code change), they escalate then — but the expected
path is straight through to `android-developer`.
